# 找找 · ZhaoZhao

Windows 单机全文检索工具：对本机硬盘、移动硬盘和网络映射盘上 1 万～10 万个文件建立内容索引，输入关键词即可看到命中位置的上下文。
需求见 [`找找-软件需求说明.html`](找找-软件需求说明.html)。

- 覆盖文本、代码、Office（含 .doc/.xls/.ppt 与 WPS）、PDF、扫描件和图片（OCR）、压缩包、邮件。
- 关键词、短语、布尔、`NEAR/n`、正则（RE2）、模糊匹配、元数据过滤。
- 移动硬盘拔掉后仍可搜索，打开时提示需要接入哪块盘；重新接入后自动增量对账。
- 所有数据只存本机，不联网。

> **当前状态**：核心引擎、界面、后台任务、OCR、容器、卷管理已实现并测试（见下方「需求覆盖」）。
> GitHub Actions 会在 Linux 和 **真实 Windows**（`windows-latest`）上跑完整测试，并在 Windows 上对打包好的完整版做冒烟测试
> （含中文路径与中文 `TEMP`：老格式转换、图片 OCR、压缩包）。
> **已在 Windows 上验证**：Windows 目录监听（`ReadDirectoryChangesW`）、卷序列号/GUID 识别、全部单元与集成测试、
> 完整版运行、安装包编译；**映射网络盘**（本机共享文件夹映射成盘符，约 270 个混合文件：文本、老格式、图片、
> 多页扫描 PDF、压缩包，默认设置）上的完整索引、搜索、诊断导出和退出（`packaging/smoke-network.ps1`）。
> **仍未在 Windows 上验证**（CI 没有桌面会话）：托盘菜单点击、全局快捷键、磁盘接入/拔出通知、电池与用户活动检测、
> 云盘占位文件识别，以及真实移动硬盘场景。请在真实桌面上做一轮验收。

### 中文检索的做法（M0 全文索引选型结论）

选用 **SQLite FTS5**，并把每个汉字作为一个独立词元写入索引（`unicode61` 分词器 + 入库前在汉字之间插入空格）：

- 单个汉字、两个字的词都能**精确**命中，不依赖分词；短语 = 连续词元，标点和空白不影响连续（OCR、PDF 常在字间夹空格）。
- 英文/数字按词索引，查询按词的开头匹配（`inv` 命中 `invoice`）。
- 归一化保证「一个字符变一个字符」，所以命中位置可直接对应原文偏移，用于高亮。
- FTS5 的 trigram 分词器对不足 3 个字的查询无法使用索引，因此没有采用。
- 文件名和内容放在同一张 FTS 表的两列（`n`、`c`）：布尔表达式可以跨列（「合同」在文件名里、「张三」在正文里），
  一次 `MATCH` 完成，并用 `bm25(fts, 1.0, 8.0)` 给文件名加权排序。

查询执行分两步：先把语法树翻译成 FTS5 表达式取候选；表达式与语义完全一致的（关键词、短语、布尔、英文模糊）直接用索引结果；
`NEAR/n`、中文模糊、正则、需要读取文本的情况，再在 Go 里对候选逐个精确校验并定位命中。
正则会从表达式中提取必然出现的**汉字**字面量缩小候选；提取不到时扫描全部已提取文本（可取消的上限由 `MaxVerify` 控制）。

## 构建与运行

需要 Go 1.26+、Node 20+（只在重建界面时需要，构建产物已提交在 `internal/web/dist`）。

```bash
# 开发（任意平台）：运行后会打印带令牌的界面地址
go run ./cmd/zhaozhao -no-ui -add /path/to/dir
# 重建界面（输出到 internal/web/dist）
cd web && npm ci && npm run build

# 交叉编译 Windows 版本并打包便携版
packaging/build-windows.sh
# 离线安装包（需要 Windows 上的 Inno Setup）
iscc packaging\zhaozhao.iss
```

### 组件

- **老格式**：doc/xls/ppt/rtf 和 WPS 的 wps/et/dps 由程序自己解析（不需要任何组件，每个文件几毫秒）；
  内置解析不了的（Word 95 等更老的版本、个别特殊文件）自动排到「老格式转换」队列交给 LibreOffice。
  「设置 → 日志与诊断 → 老格式测试」可抽样比较内置解析和 LibreOffice 的结果。
- **LibreOffice**：放到 `components\libreoffice\program\soffice.exe`，或直接安装 LibreOffice（自动查找）；
  环境变量 `ZHAOZHAO_SOFFICE` 可指定路径。每个转换子进程常驻一个 LibreOffice，经 Python-UNO 桥逐个转换
  （用 LibreOffice 自带的 Python；Linux 需要 `python3-uno`），没有 Python-UNO 时退回每个文件单独启动。
- **PDFium**：`components\pdfium\pdfium.dll`（完整版和精简版都随包附带）；环境变量 `ZHAOZHAO_PDFIUM` 可指定路径。
  用它提取 PDF 文字层，并把扫描页渲染成图片做 OCR（JBIG2、JPEG 2000 等格式都能识别）；没有它时用纯 Go 解析器。
- **OCR**：把 [RapidOCR-json](https://github.com/hiroi-sora/RapidOCR-json) 放到 `components\ocr\`；
  或用 `ZHAOZHAO_OCR="命令 参数…"` 指定任何兼容**管道协议**的程序（见 `tools/ocr_bridge.py`，它用 `rapidocr-onnxruntime` 实现了同一协议，开发测试用）。
  没有 OCR 组件时，图片只索引文件名，扫描 PDF 只索引文字层并标记「需要 OCR」。
- 数据目录：`%LOCALAPPDATA%\ZhaoZhao`（便携版为程序旁的 `data`），含 `index.db`、`config.json`、`roots.json`（索引根备份）、`zhaozhao.log`（异步写入，按 10 MB 滚动，旧日志压缩为 `.gz`，保留 5 个）、`crash.log`（程序崩溃报告）。
  「设置 → 日志与诊断」可切换日志详细程度、导出诊断信息（可隐藏文件名和路径）。建索引期间日志里每 10 分钟汇总一次
  各阶段用时（读文件和查重、提取、等写入、写入速度、OCR 页数），诊断信息注明各个盘是固态还是机械硬盘。

### 实测数据（4 核 / 15 GB 内存的云主机，固态存储；合成文档平均约 1.2 千字）

| 指标 | 需求目标 | 实测（10 万篇） |
|---|---|---|
| 关键词 / 短语 / 布尔首屏 | P95 ≤ 300 ms | 10～45 ms；极端的高频单字（命中全部 10 万篇）239 ms |
| 英文前缀（命中 9.8 万篇） | — | 212 ms |
| 带过滤的查询（ext + size） | — | 14 ms |
| `NEAR/n`、中文模糊（有候选范围） | 模糊 ≤ 1 s | 23～32 ms |
| 英文模糊 | ≤ 1 s | 命中少量文档时几毫秒；**命中几乎全部文档的极端情形 1.7 s** |
| 正则（含汉字字面量） | ≤ 2 s | 23 ms |
| 正则全量扫描 10 万篇已提取文本 | ≤ 60 s（待校准） | 8.5 s |
| 索引占用 | ≤ 提取文本的 2 倍 | 约 1 倍（296 MB 对应约 300 MB UTF-8 文本） |
| 文件名 + 内容入库（不含解析） | — | 约 650 篇/秒（单线程） |
| 软件启动到可以搜索（已有索引，Linux 实测） | ≤ 2 s | 71 ms |

未实测：加入索引根后按文件名可搜的时间、快捷键呼出耗时、主程序空闲内存（需要真实 Windows 环境和 10 万个真实文件）。

### 其他 M0 验证项的结论

| 验证项 | 结论 |
|---|---|
| 老格式 | 0.2.0 起内置解析：doc（片段表、页眉页脚、脚注尾注、批注、文本框，去掉域代码）、xls（BIFF8：共享字符串跨 CONTINUE、数字/日期格式、公式结果、批注、隐藏工作表）、ppt（只读当前有效的幻灯片和备注，不读母版占位文字）、rtf（按字体字符集解码 GBK 等，`\uN`）。样本上与 LibreOffice 转换结果的文字覆盖率 100%，每个文件几毫秒；模糊测试 15 万次无崩溃、无卡死。`.wps/.et/.dps` 只用「改扩展名的 doc/xls/ppt」验证过，**没有真实 WPS 样本**（可用「老格式测试」在用户电脑上抽样统计）。内置解析不了的交给常驻 LibreOffice，每个文件约 0.05～1 秒。 |
| OCR | RapidOCR（PaddleOCR 模型，CPU）经管道协议接入：简体中文 + 英文识别正确，包括 jpg/png/bmp/webp、多页 LZW TIFF、扫描 PDF（逐页）。每张约 1 秒量级（Linux 云主机，含常驻进程摊销），**未做大样本准确率评测**。每个进程的线程数用 `--numThread` 指定；0.2.3 起在每台电脑上用随包的 A4 扫描样张实测选择「进程数 × 线程数」（`zhaozhao --ocr-bench 结果.txt` 可单独运行）；0.2.4 起按实测的每线程效率估算各种搭配，线程预算减半时也用满，有超线程的电脑还比较用上全部逻辑处理器的搭配。4 核云主机上实测每分钟页数：1 个进程 × 4 线程 16、2×2 20、4×1 26；只用 2 个核时 1×2 11、2×1 13；线程总数超过核心数反而变慢（8×4 只有 8）。Windows 测试机（2 核）上用随包的 RapidOCR-json 实测：2×1 每分钟 17.5 页、1×2 14.0 页，每个 OCR 进程连同它的解析进程约 400 MB；完整版打包流程每次都跑一遍。 |
| PDF | 0.2.0 起用 PDFium（运行时加载 DLL，不需要 cgo）提取文字层；扫描页整页渲染成 200 dpi 灰度图再 OCR，JBIG2、JPEG 2000、CCITT 等格式都能识别（已用 JPEG 2000 扫描页验证）。没有 PDFium 时退回 `ledongthuc/pdf` + `pdfcpu`。 |
| 压缩包 | zip（含 GBK 文件名）、7z（含加密头检测）、tar/gz/tgz 已验证；rar（`nwaples/rardecode`）因没有样本**未验证**。内部文件逐个读取、用完即删，不会整体解压到磁盘。0.2.2 起 zip 条目支持 Deflate64（自带解码器，由标准库 flate 改写，与 Python inflate64 逐字节核对）、BZip2、LZMA、zstd、xz；PPMd 写明不支持。 |
| 邮件 | eml（RFC2047 主题、GB2312+base64 正文、附件）、mbox 已验证；`.msg`（`mscfb`）按文件格式实现但**没有真实样本，未验证**；pst/ost（P2）未实现。 |

### 非功能与部署

- ✅ 解析/转换/OCR 在子进程中运行，超时、崩溃只记失败；SQLite WAL 事务；日志滚动；不联网（也没有检查更新功能）。
- ✅ 删除索引根/卷时同时删除提取文本；数据目录可通过 `-data` 修改。
- 🟡 长路径依赖 Go 标准库对 `\\?\` 的自动处理；LibreOffice 子进程用 ASCII 临时副本规避路径问题。
- ✅ 安装包：`packaging/zhaozhao.iss`（含卸载时询问是否保留索引）在 CI 的 Windows 上编译通过；安装/卸载流程本身未实测。
